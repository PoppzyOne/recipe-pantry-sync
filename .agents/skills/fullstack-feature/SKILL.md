# Full-Stack Feature Scaffolding (Skafferiet)

Follow this ordered workflow whenever adding or modifying a domain feature across the backend and frontend.

## 1. Database Migration (`backend/src/main/resources/db/migration/`)
1. Check existing migrations (`V1.0.0__init_schema.sql` through `V1.0.3__shopping_list.sql`) and pick the next semantic version (`V1.0.x__<feature_name>.sql`).
2. Write SQL that is 100% compatible with **both PostgreSQL 16 (production) and H2 (`%dev`/`%test`)**:
   - Use standard `BIGSERIAL` / `GENERATED BY DEFAULT AS IDENTITY`, `VARCHAR`, `BOOLEAN`, `DOUBLE PRECISION`, `DATE`, and `TIMESTAMP`.
   - Avoid PostgreSQL-only extensions or syntax not supported by H2 in standard mode.

## 2. Backend Layer (`backend/src/main/java/com/recipesync/`)
Always follow the strict `Resource -> Service -> Repository -> Entity` architecture:
1. **Entity (`entity/`):** Extend `PanacheEntity` or define standard JPA `@Entity` annotations matching the Flyway migration.
2. **Repository (`repository/`):** Implement `PanacheRepository<T>` with `@ApplicationScoped`. Encapsulate custom queries here rather than in the service.
3. **DTOs (`dto/`):**
   - Use immutable Java `record`s for all request and response payloads (`Create*Dto`, `Update*Dto`, `*ResponseDto`).
   - Add Jakarta Bean Validation annotations (`@NotBlank`, `@NotNull`, `@Positive`, `@Size`).
   - **Never** expose JPA entities directly in REST resources.
4. **Service (`service/`):** Annotate with `@ApplicationScoped`, inject repositories via constructor `@Inject`, mark mutating methods `@Transactional`, and map entities to `record` DTOs.
5. **Resource (`resource/`):** Annotate with `@Path("/api/...")`, `@Produces(MediaType.APPLICATION_JSON)`, `@Consumes(MediaType.APPLICATION_JSON)`, and use `@Valid` on incoming DTO parameters.
6. **Integration Tests (`backend/src/test/java/com/recipesync/`):** Add `@QuarkusTest` REST-assured tests covering happy paths, validation errors (`400`), and not-found cases (`404`).

## 3. Frontend Layer (`frontend/src/`)
Ensure 1:1 structural parity between Java `record` DTOs and TypeScript interfaces:
1. **Types (`src/types/<domain>.ts`):** Define strict TypeScript `interface`s and union types that match the JSON serialization of the backend Java `record`s.
2. **API Client (`src/api/<domain>Api.ts`):** Implement typed `fetch` functions with explicit HTTP status checks and user-friendly error messages.
3. **Pinia Store (`src/stores/<domain>Store.ts`):**
   - Expose reactive state, loading/error states, and async actions wrapped in `try/catch`.
   - If the feature impacts in-store usage (shopping list or meal plan), persist state to `localStorage` and support optimistic UI updates.
4. **Vue Components (`src/components/`):** Use `<script setup lang="ts">` and Tailwind CSS v4 utility classes directly in templates.
5. **Unit Tests (`src/__tests__/`):** Add Vitest tests for new store and component logic.
